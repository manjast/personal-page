When I ran an enterprise AI procurement in 2026, the model selection took 5 minutes. The procurement questions took 5 hours.

The workload was bounded. The cost ceiling was set. The shortlist came from the previous cost-discipline analysis: five cost-competitive models that matched the workload and cost ceiling — DeepSeek V4-Pro, GLM 5.2, Kimi K2.6, MiniMax M3 and MiMo-V2.5-Pro.

What I had not run before was the procurement review that followed the model shortlist. Five hours of it. Five surprises — and one synthesis worth spelling out.

GPT-5.6 and Fable 5 entered the procurement review for a different reason: they showed how access approval, fallback behavior and model capability are not the same decision. The shortlist was the cost-compatible tier. GPT-5.6 and Fable 5 were procurement boundary cases.

The model was rarely the constraint. The procurement was.

## The procurement path stack

Each of the five findings below is one layer of a procurement path the model shortlist has to survive. The five sections below list them; the stack is the reason they form one decision, not five independent ones.

## 1. Multi-cloud is the first fork, not the second

AWS Bedrock docs list 18 first-party model providers as of July 2026. That is provider count, not foundation-model count; AWS separately describes access to hundreds of FMs. Azure AI Foundry and Vertex Model Garden carry their own rosters. Self-hosting open weights on European cloud is a fourth path.

Most teams default to Bedrock without realizing they have three other options that change data residency, billing model and lock-in posture. The default is itself a procurement decision. Per-vendor pricing tiers differ; per-region inference routing differs; per-provider contract terms differ, especially around export-control variants and per-customer approval.

The procurement team's first questionnaire should distinguish all four before shortlisting models.

## 2. Z.ai on BIS as a routing decision, not a binary block

Z.ai, the company behind GLM-5.2, has been on the BIS Entity List since January 2025. The open-weight model at the top of AA Intelligence Index v4.1 (51, 2026-06-15) is, for US persons, blocked at the API level. For EU enterprises the question becomes which deployment path.

A BIS-restricted Chinese provider turns API access into a jurisdiction question. The data-residency answer comes from the deployment path, not from the model name: first-party API, European-hosted inference, or self-hosting open weights are different compliance postures for the same model.

This is the procurement insight most teams miss. Regulatory friction that looks like a binary block is often a routing decision, not a "yes/no" answer.

## 3. GPT-5.6 per-customer approval queue

OpenAI launched GPT-5.6 Sol on June 26, 2026 in preview. Per OpenAI's post: "available to select trusted partners in preview. Broad availability coming soon." Per Axios coverage the same day: approximately 20 partner organizations at launch. Three tier names: Sol, Terra, Luna, at $5/$30, $2.50/$15 and $1/$6 per 1M tokens, all preview-only.

The procurement question for EU enterprises is no longer "can we afford the frontier?" It is "can we even get it?" Per-customer US government approval gates access, not price. Procurement no longer chooses between models; it chooses between access tiers.

The 20-partner number is corroborated by Reuters, CNBC and TechCrunch, each describing the launch as a small vetted preview rather than a press estimate. The operating constraint is not the exact count. It is that frontier access can be approval-gated before it is price-gated.

## 4. The Fable 5 Fallback API: your model depends on the query

Claude Fable 5 was suspended on June 12 under a US export-control directive and redeployed globally on July 1. The access question changed from "can we use Fable?" to "does Fable answer this request?". Anthropic's Fallback API is still active: flagged cybersecurity, biology, chemistry and distillation requests can route from Fable 5 to Opus 4.8 instead.

The model the developer requested is not always the model that answers. The contract says Fable 5. The operational path can land on Opus 4.8 for an entire class of requests. The cost model, the compliance model and the latency profile all follow the answering model, not the contracted model.

The Cyber Verification Program is an Anthropic-managed approval process that lives at the Opus/Sonnet safeguard layer, not at the Fable layer. It matters to Fable only through the fallback chain: a Fable request that becomes an Opus fallback answer can hit an Opus cyber safeguard, and CVP is the formal approval path for legitimate defensive cyber work in that case. Treat CVP as an operational access process, not as a model capability. Procurement should spec the operational path, not just the API tier.

For API customers, fallback is a configuration choice. For Claude and Claude Code users, automatic model switching is part of the product behavior. Either way, the named model and the answering model can differ for an entire class of requests.

## 5. Self-hosting open weights is the under-evaluated path

For latency-insensitive, high-volume, internal document workflows, the cost economics on European cloud flipped in the last six months. DeepSeek V4-Pro and GLM-5.2 at self-host hardware costs versus Bedrock pass-through billing, plus the data-residency benefit, plus the eval-portability benefit, beat hosted pass-through at scale.

The procurement error most teams make is treating all cost-competitive models as the same procurement path. Self-hostable open weights, for example DeepSeek V4-Pro, GLM-5.2 and MiMo-V2.5-Pro, are one path. Proprietary hosted but cost-competitive models, for example Qwen3.7 Max on Alibaba's stack, are a different path. Different capex, different data-residency posture, different eval-portability story. Most enterprises skip the distinction because the procurement team does not run a hosting questionnaire. They should.

The economics work above a workload threshold that is consistent across the cost-competitive tier. Below that threshold, hosted pass-through is usually cleaner. Above that threshold, self-host wins on cost-per-task at scale, assuming the team's eval suite remains portable across deployment paths.

## Synthesis: the unified wall of friction

Read separately, the five findings look independent: multi-cloud routing, BIS routing, GPT-5.6 approval, Fable fallback, self-host economics. Read together, they form a wall of friction layered around the same procurement decision. Each surface adds a new dimension. Each one is enough to derail a single-procurement decision. Together, they form the procurement posture for 2026 enterprise AI.

If the cloud-platform fork is step one — which provider hosts — the export-control layer is step two — which regulatory domain the data crosses. The per-customer approval queue is step three — which models the team has access to. The Fable fallback is step four — which model actually answers a given query. The self-host economics is step five — which workload stays cheaper at scale.

Most procurement cycles stall between step two and step three, precisely where the cost calculation cannot yet be made because access is gated. The five hours I spent were spent mostly there.

## Operational pattern

For teams in the same posture:

1. Distinguish the four hosting paths (Bedrock, Azure AI Foundry, Vertex Model Garden, self-host) before shortlisting models.
2. Treat BIS-as-feature or BIS-as-blocker as a per-model routing decision, not a global policy.
3. For frontier models (GPT-5.6, Claude Fable 5, Claude Mythos 5), separate access status from model capability. Procurement decision becomes: do we need this specific model, or do we need what we can reliably operate?
4. For the queries that trigger Fallback API routing or any other conditional-answer mechanism, cost projections should account for the answering-model path, not only the contract-model path.
5. Run the hosting-questionnaire exercise for self-host-eligible workloads. Most teams will find 1-2 paths that pass.

The five-hour procurement review taught this. The operational follow-up is the next post: the architectural patterns that survive these procurement shifts.
